# CBL-2.6. План счетов: мерчантские, clearing, комиссии, выплаты, suspense

| Поле | Значение |
| :-- | :-- |
| Эпик | E2, Ledger |
| Репозиторий | `cbl-ledger` |
| Размер | M |
| Волна и параллельная группа | W1-LEDGER |
| Зависит от | 2.1, 2.4 (внутренний провижининг), CF-1 |
| Версия контрактов | `cbl-protos@cf-1` (gRPC не меняется; см. ADR-2.6) |
| Статус | done, ревью закрыто |

## 1. Контекст и цель

План счетов леджера: пять типов счетов (`merchant`, `clearing`, `fee`, `payout`,
`suspense`), правила их существования и способ получения `account_id` потребителями
(consumer 2.7, Payout 10.2, Billing API 7.4). Задача закрывает открытый вопрос 2.4:
провижининг счетов выполнялся SQL-севом в тестах и точечно (счет выплат при коммите).

Главное ограничение: gRPC-контракт CF-1 (`LedgerService`) не содержит методов управления
счетами, а замороженные `PostTransaction`/`Reserve`/`GetBalance` принимают готовый
`account_id`. Значит, `account_id` обязан быть вычислим потребителем из бизнес-ключа без
дополнительного RPC (ADR-2.6).

## 2. Границы

In scope: план счетов (типы, обязательность `merchant_ref`, актив, decimals), канонический
бизнес-ключ и детерминированный `account_id` (UUIDv5), идемпотентный провижининг
(`EnsureAccount`), переход внутреннего провижининга счетов выплат (2.4) на план, golden
векторы для потребителей.
Out of scope: шаблоны проводок для бизнес-событий (2.7), новые gRPC-методы, изменение
миграций 00001 - 00008, партиционирование.

## 3. Функциональные требования

FR-1. Бизнес-ключ счета: `(type, asset, decimals, merchant_ref)`. Правила плана:

| Тип | `merchant_ref` | Назначение |
| :-- | :-- | :-- |
| `merchant` | обязателен | баланс мерчанта по активу (Dr clearing / Cr merchant при `payment.completed`) |
| `payout` | обязателен | счет выплат мерчанта (получатель `CommitReserve`) |
| `clearing` | запрещен | транзитный прием платежей платформы по активу |
| `fee` | запрещен | комиссии платформы по активу |
| `suspense` | запрещен | расхождения сверки по активу |

Валидация: `type.Valid()`, `asset` вида `^[A-Z0-9]{1,16}$`, `decimals` 0 - 18,
`merchant_ref` вида `^[A-Za-z0-9_-]{1,128}$` (без двоеточий: ключ сериализуется
двоеточиями), для `merchant`/`payout` - обязателен, для остальных - пуст.

FR-2. Детерминированный `account_id` (ADR-2.6): UUIDv5 (SHA-1) от канонического имени

```
cbl:ledger:account:v1:<type>:<asset>:<decimals>:<merchant_ref>
```

в стандартном namespace `uuid.NameSpaceURL`. Одинаковый бизнес-ключ всегда дает один и тот
же `account_id` в любом сервисе; golden-векторы (раздел 4) позволяют проверить реализацию
без общей библиотеки. Детерминированность распространяется только на вновь создаваемые
счета: существующие строки с бизнес-ключом, но другим `id` (legacy, dev-данные) остаются
валидными, `EnsureAccount` возвращает их как есть.

FR-3. `EnsureAccount(type, asset, decimals, merchant_ref)`: идемпотентный провижининг.
Алгоритм: поиск по бизнес-ключу -> при наличии сверка `decimals` (`account_conflict` при
расхождении) и возврат строки; при отсутствии - вставка счета с детерминированным `id` и
балансового ряда нулем в одной транзакции БД; погашенная уникальным индексом вставка
(гонка) перечитывает каноническую строку по ключу - победитель определяет и счет, и
балансовый ряд. Лечение балансового ряда допускается только у счетов без проводок: счет с
`entries`, но без `balances`, - порча данных, провижининг отдает `account_not_found`, а не
маскирует ее нулем. Ошибки: `invalid_account_plan` (нарушение правил FR-1),
`account_conflict` (существующий счет с другими параметрами); на границе `CommitReserve`
(2.4) конфликт decimals отображается в `asset_mismatch`. Проверка типа счета для резервов
(2.4) и fail-closed по `merchant_ref` сохраняются.

FR-4. Внутренний провижининг 2.4 переводится на план: `CommitReserve` получает счет выплат
через `EnsureAccount` (детерминированный `id` вместо случайного UUIDv7); существующие
счета выплат с иным `id` переиспользуются без ошибок.

FR-5. Usecase предоставляет `EnsureAccount` (для consumer 2.7 и Payout-запросов внутри
сервиса); внешний gRPC-контракт не меняется. Потребители, которым нужен `account_id`
(Billing API, Payout), вычисляют его по FR-2; чтение отсутствующего мерчантского счета
трактуется потребителем как нулевой баланс (контракт `GetBalance` не меняется).

## 4. Контракты

gRPC/Protobuf не изменяются (CF-1). Кросс-сервисный контракт плана счетов - алгоритм FR-2
плюс golden-векторы; фиксируется в `CBL-003` (раздел 1, примечание об идентификаторах, и
новый подраздел "План счетов леджера"). Векторы:

| Бизнес-ключ | account_id |
| :-- | :-- |
| `clearing/USDT/2/` | `dec27141-ec8f-55de-a325-04a35cd6b0f2` |
| `fee/USDT/2/` | `b138b712-5940-59bc-82bd-19f653642227` |
| `fee/USDT/0/` | `8ee4265f-342c-5dbc-8d80-2516a5641b59` |

## 5. Модель данных и миграции

Схема не меняется (миграции 00001 - 00008 не трогаются): `accounts.id` уже `uuid PRIMARY
KEY`, бизнес-ключ защищен уникальным индексом `accounts_type_asset_merchant_idx`. Новые
правила плана обеспечиваются валидацией и единственным провижининг-путем; прямой SQL в
обход плана возможен (trade-off T-LED-07), денежные инварианты при этом не нарушаются
(резервы fail-closed, транзакции сбалансированы).

## 6. Конечные автоматы

Не применимо: счета не меняют состояние; изменение `decimals` или `merchant_ref` запрещено
(сверка при провижининге).

## 7. Edge cases

Повторный `EnsureAccount` (тот же `id`), конкурентный провижининг (гонка вставки, в том
числе с разными `decimals`: победитель занимает ключ, проигравшие получают
`account_conflict`, сырых ошибок БД наружу нет), тот же бизнес-ключ с другими `decimals`
(`account_conflict`; тот же актив с другой шкалой, но свободным ключом - другой счет),
нарушение правил плана (актив, длина/символы `merchant_ref`, `merchant_ref` у
платформенного типа, отсутствие `merchant_ref` у мерчантского), legacy-строка со случайным
`id`, счет с проводками без балансового ряда (отказ лечения), нулевой баланс нового счета,
совместимость с `CommitReserve` и `Reserve` (2.4).

## 8. Нефункциональные требования

Провижининг - одна короткая транзакция (поиск + вставка), вызывается на «холодном» пути
первой операции; гонки закрыты уникальным индексом без глобальных локов. Покрытие
unit+integration не ниже 80%; golden-векторы закрепляют контракт.

## 9. План тестов

| Уровень | Сценарии |
| :-- | :-- |
| Smoke | `go build ./...`; compose-стенд без изменений схемы (версия 8) |
| Unit | domain: валидация ключа по типам, детерминированность и golden-векторы (включая BTC/8, decimals 0, ref с `_`), helpers ключей |
| Integration (storage) | EnsureAccount: создание, повтор, конкурентный вызов, гонка с разными decimals, конфликт decimals, legacy-строка, правила плана, лечение балансового ряда и отказ при проводках; CommitReserve использует детерминированный счет выплат |
| Integration (gRPC, bufconn) | bufconn-сев через `EnsureAccount`; PostTransaction/GetBalance/Reserve по счетам провижининга; сверка выведенного id с планом |
| E2E (compose) | счета через провижининг и фондирование проводкой Dr clearing / Cr merchant (без SQL); Reserve/Commit/Release и ListEntries |
| Load | не расширяется |

## 10. План работ и коммит

Коммит `CBL-2.6: детерминированные счета и провижининг плана счетов`; спека входит в
коммит; `CBL-003` (примечание об идентификаторах, раздел 9 и векторы) и `CBL-000`
(раздел 6, строка про счета) синхронизированы.

## 11. Открытые вопросы и решения

- ADR-2.6: детерминированные `account_id` (UUIDv5 от бизнес-ключа) вместо RPC
  `EnsureAccount`: контракт CF-1 заморожен и не содержит управления счетами; вычисление на
  стороне потребителя убирает зависимость и лишний round-trip; цена - отступление от
  "UUIDv7 для всех сущностей" (зафиксировано примечанием в `CBL-003`, раздел 1) и
  необходимость golden-векторов против расхождения реализаций. Реализация живет в
  `internal/domain` леджера; потребители (Billing API 7.4, Payout 10.2) обязаны
  воспроизводить алгоритм по векторам - перенос в общую библиотеку `cbl-kit` запланирован
  до старта этих задач (KI-ledger-08).
- ADR: канонические `decimals` актива задает первый провижининг (событие платформы);
  единый реестр активов - вне рамок 2.6; расхождение шкал между сервисами приводит к
  разным счетам, диагностируется через `account_conflict` и алерты (runbook).
- Принято: legacy-счета с тем же бизнес-ключом, но другим `id`, переиспользуются;
  потребительский вывод id для legacy-данных не работает, мост - только ops/SQL; prod
  стартует на пустом реестре счетов, dev-стенды пересоздаются (`down -v`).
- ADR: лечение балансового ряда только у счетов без проводок; счет с `entries` без
  `balances` - порча, отдается `account_not_found` (не маскируется нулем).
- Примечание: субсчета шардинга (2.9, раздел 3.2; задача 14.6) потребуют версии схемы
  ключа (`v2` префикса) или отдельного поля; взаимодействие фиксируется в 14.6.
- ADR: правила плана проверяются валидацией и провижининг-путем, но не CHECK-ограничением
  БД: миграция с CHECK сломала бы уже примененные dev-стенды, а денежные инварианты не
  затрагиваются (T-LED-07).
- Открытый вопрос: шаблоны проводок бизнес-событий (`payment.completed`: Dr clearing /
  Cr merchant, комиссия) - задача 2.7.
- Открытый вопрос: отображение "счета нет -> нулевой баланс" в Billing API - задача 7.4.

## 12. Ревью (CBL-001, шаг 6)

Четыре независимых прохода (14.10.2026). Блокеров нет; majors (гонка вставки с разными
decimals, размещение и дрейф вывода id, bufconn-сценарий, T-LED-07) закрыты, minor
закрыты или зафиксированы.

| Роль | Ключевые замечания | Закрытие |
| :-- | :-- | :-- |
| Без контекста | гонка подавленной вставки вставляет баланс по выведенному, а не каноническому id (FK-ошибка вместо `account_conflict`); противоречие FR-3 (`asset_mismatch` vs `account_conflict`); нет тестов гонки и границ; мертвая проверка decimals | дочитывание канонической строки до балансового ряда, порядок исправлен; FR-3 синхронизирован; тесты гонки смешанных decimals, порчи без balances, границы валидации; недостижимая проверка удалена |
| Архитектуры | major: реализация вывода id не закреплена общей библиотекой, векторы узкие; major: ошибочные decimals навсегда занимают ключ без плана; major: legacy-строки нарушают "один ключ - один id" для потребителей; T-LED-07 отсутствует; конфликт с субсчетами 2.9 | векторы расширены (BTC/8, decimals 0, `M-1_a`); KI-ledger-08 (перенос в `cbl-kit` до 7.4/10.2) и runbook-процедура `account_conflict`; legacy-граница зафиксирована (prod на пустом реестре, dev - пересоздание); T-LED-07 добавлен; взаимодействие с 14.6 отмечено |
| С контекстом | bufconn-строка плана тестов не выполнена (сев SQL); T-LED-07; мертвая проверка; SQL-фондирование e2e; неоднозначность §7 о decimals; зависимости спеки | `seedGrpcAccount` переведен на `EnsureAccount` + тест сверки id; T-LED-07 добавлен; проверка удалена; e2e фондируется проводкой Dr clearing / Cr merchant; §7 и зависимости уточнены |
| Безопасности | major: каноничность decimals между сервисами не закреплена; гонка вставки дает Internal; dirty legacy ломает CommitReserve (Internal); лечение маскирует порчу; предсказуемые id - не capability (KI-ledger-02); нет теста legacy payout | decimals/реестр зафиксированы в §11 + CBL-003; гонка исправлена; `invalid_account_plan`/`account_conflict` замаплены в failed_precondition; лечение ограничено счетами без проводок; формулировка KI-ledger-02 расширена; тест legacy payout уже есть (`TestIntegrationCommitReusesExistingPayoutAccount`) и дополнен сверкой наследования |
