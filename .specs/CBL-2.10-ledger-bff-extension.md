# CBL-2.10. Расширение Ledger gRPC для BFF-выписок

| Поле | Значение |
| :-- | :-- |

| Размер | S |

| Зависит от | 2.5 (выписка), CF-3, тег `cbl-protos@cf-3.2` |

## 1. Контекст и цель

Ревью 7.1 (BLOCKER архитектуры) выявило: `/balances` и `/ledger/entries` Billing
API не реализуемы на контракте CF-1 - нет списка счетов мерчанта с балансами и
ownership-проверки, нет фильтра выписки по мерчанту и периоду. 2.10 добавляет
аддитивные RPC и поля в Ledger gRPC (зафиксированы коммитом `cbl-protos`
`CBL-2.10`, тег `cf-3.2`) и реализует серверную часть, после чего 7.4 получает
источник данных без общих таблиц и независимо от KI-01.

## 2. Границы

In scope: `ListMerchantAccounts` (счета мерчанта с балансами и ownership),
`ListEntries` с `merchant_ref` и периодом, валидация недоверенного ввода,
integration и e2e тесты. Out of scope: REST Billing API (7.4), агрегация
`pending` (Payment, 7.4), ретеншен/партиционирование (14.2), схема БД не
меняется (только чтения).

## 3. Контракт (cf-3.2)

- `ListMerchantAccountsRequest{merchant_ref}` ->
  `ListMerchantAccountsResponse{accounts[]}`; `MerchantAccount{account_id, type,
  asset, decimals, available, reserved}`; порядок `(asset, type)`, счета без
  проводок - нулевые.
- `ListEntriesRequest` + `merchant_ref = 4`, `period_from = 5`, `period_to = 6`;
  заполняется `account_id` или `merchant_ref` (хотя бы одно); период - по
  `created_at` транзакции, `from` включительно, `to` исключительно.

## 4. Функциональные требования

FR-1. `ListMerchantAccounts`: обязательный `merchant_ref` по правилам плана
счетов (`^[A-Za-z0-9_-]{1,128}$`); возвращаются только счета типов `merchant` и
`payout` этого мерчанта (платформенные счета недоступны); балансы читаются
LEFT JOIN balances (отсутствие ряда - нули).

FR-2. `ListEntries`: при `merchant_ref` выписка ограничена счетами мерчанта
(`merchant`, `payout`); `account_id` чужого мерчанта или платформенного счета
под фильтром мерчанта отвечает `NotFound` без раскрытия существования
(fail-closed); `account_id` без фильтра работает как в 2.5 (внутренние
вызовы); пустой фильтр и невалидный `merchant_ref` - `InvalidArgument`
(`invalid_query`); инверсные границы периода - `InvalidArgument`
(`invalid_period`).

FR-3. Период: `period_from` включительно, `period_to` исключительно по
`t.created_at`; курсор 2.5 сохраняется (entry_id, строковый), пагинация
непротиворечива при конкурентных записях.

FR-4. Транспорт валидирует недоверенный ввод до хранилища: UUID `account_id`,
формат `merchant_ref` (через `domain.ValidMerchantRef`), валидность
`Timestamp` (CheckValid), длина курсора, порядок границ.

FR-5. Тесты: unit - валидация транспорта (пустой фильтр, битые ref/период,
пустой merchant_ref); integration - изоляция мерчантов (свои и чужие счета,
платформенные), период (границы включительно/исключительно, back-date через
append-only INSERT), порядок и нулевые балансы `ListMerchantAccounts`,
пагинация; gRPC bufconn - сквозной сценарий мерчанта; e2e compose -
`ListMerchantAccounts` и мерчантская выписка на реальном gRPC+PostgreSQL.

## 6. Нефункциональные требования

Только чтения: схема данных не меняется, добавлена миграция 00009 (частичный
индекс `accounts (merchant_ref, type, asset) WHERE merchant_ref IS NOT NULL`) -
выборка счетов мерчанта и join-фильтр выписки идут по нему; выписка по счетам
мерчанта - join к `entries` через `entries_account_idx` (2.5). Полноценный
бенчмарк мультисчетной выписки - профиль 14.1/14.2 (как и нагрузка чтений 2.5);
дедлайн 500 мс (CBL-000, раздел 3) при типовых объемах держится, EXPLAIN
ревью подтвердил SEQSCAN только на прежнем индексе - лечится 00009.
Ответы ограничены: выписка - кламп 200 (2.5), список счетов - предел 1000
(ErrTooManyResults - аномалия плана счетов); права: gRPC-порт не публикуется
вне доверенной сети (KI-ledger-02).

## 7. Edge cases

Мерчант без счетов - пустой список (не 404); счет без балансового ряда
(аномалия провижининга) - нули в списке, точечный GetBalance остается
fail-closed (2.5); чужие/платформенные счета под мерчантским фильтром -
NotFound; `to` раньше или равен `from` (пустой период) - InvalidArgument;
курсор из другой выписки принимается (фильтр по entry_id, 2.5); в пределах
одного счета сохраняется гарантия 2.5 «нет пропусков конкурентных записей»
(сериализация CAS баланса); в мультисчетной выписке мерчанта такой
сериализации нет: запись, закоммиченная после выдачи курсора с меньшим
entry_id, может не попасть в текущий обход (стандартная семантика курсора,
повторная выписка по периоду ее показывает) - зафиксировано осознанно;
back-date тестовых строк - только INSERT (append-only журнал).

## 8. Ревью (CBL-001, шаг 6)

Четыре независимых прохода (15.10.2026). Блокеров нет: fail-closed изоляция
подтверждена (чужой, платформенный и несуществующий account_id под фильтром
мерчанта дают одинаковый NotFound), SQL-инъекций и утечек нет, деньги только
int64+decimals. MAJOR закрыты: коды ошибок приведены к каталогу спеки/runbook
(`invalid_query`, `invalid_period`; `missing_merchant_ref` для пустого списка);
добавлен индекс миграции 00009 (EXPLAIN ревью показал SEQSCAN accounts на
прежнем индексе - утверждение НФТ исправлено на фактическое); введен предел
списка счетов (1000, `ErrTooManyResults` - resource_exhausted); семантика
пагинации мультисчетной выписки задокументирована (окно гонки, §7); фильтр
выписки перенесен в `usecase.ListEntriesFilter` (транспорт больше не импортирует
storage). MINOR/NIT закрыты: тесты невалидного Timestamp (CheckValid), пустого
списка и счета без балансового ряда, unit-тесты `ValidMerchantRef`, кейсы
`mapError` (`invalid_query`, `too_many_results`), `merchantAccountTypes` -
массив, формулировки комментариев, smoke-скрипт обновлен на версию 9, журнал
2.8 получил хэш. Принято осознанно: `COALESCE` нули для счета без ряда (2.5

`account_id` без `merchant_ref` остается внутренним путем (обязанность 7.4 -
всегда передавать `merchant_ref` субъекта токена, T-LED-11); отсутствие
пагинации списка счетов (число счетов - активы на мерчанта, ограничено).

## 9. Решения и открытые вопросы

- KI-ledger-08 (перенос вывода `account_id` в `cbl-kit`) не блокирует 2.10:
  сервис работает с уже существующими счетами; BFF получает их списком.
- KI-ledger-02: ownership реализован через `merchant_ref` фильтром, но
  non-authenticated gRPC сохраняет статус до mTLS (0.6) - prod запрещен;
  обязанность 7.4 - всегда выводить `merchant_ref` из субъекта токена и не
  проксировать клиентский `account_id` без фильтра (T-LED-11).
- Агрегация `pending` для `/balances` - данные Payment (7.4), не Ledger;
  маппинг 7.4: `available`/`reserved` - сумма merchant-счетов по активу
  (reserved учитывается на счете-источнике удержания, T-LED-06), payout-счета
  в балансы не суммируются (средства в процессе выплаты).
- Список счетов без пагинации (число счетов мерчанта - активы x 2, предел
  1000); пагинация - аддитивно (cf-3.x) при появлении требования.
- Полноценный бенчмарк мультисчетной выписки и ретеншен - профиль 14.1/14.2.
